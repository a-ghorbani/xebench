# Engine profiles — why each engine exists, where it shines, and whether we measure it there

This is the doc that gives the cross-engine comparison meaning. A tokens/sec table without this context is worse than useless — it quietly misleads, because each engine is built for a *different* job and shows its worst face when benchmarked outside its purpose.

**The rule this doc enforces:** a fair comparison runs each engine on its *intended* path. Benchmarking an accelerator-first engine (LiteRT, GENIE-X) only on CPU, then publishing the number, is the same unfairness as comparing one engine's Q4_K_M against another's Q4_0 — just moved to the backend axis. Every engine profile below ends with an honest **"Are we measuring it where it shines?"** verdict. Any ❌ is a coverage bug to fix, not a result to publish as-is.

The board measures three models on every engine that has a file for them: **Gemma 4 E2B**, **Qwen3 1.7B** and **Gemma 3 1B**, on the POCO F8 Ultra (Snapdragon 8 Elite Gen 5), the Galaxy S23 (Snapdragon 8 Gen 2 for Galaxy) and the Pixel 9 (Google Tensor G4). Each engine's rows come from one measurement set: llama.cpp b11804 with llama.rn 0.13.0-rc.8, LiteRT-LM 0.18.1, ExecuTorch 1.4.1 with react-native-executorch 0.10.7, and geniex-android 0.8.0, all measured in November 2026. Every lab row prefills the same 519-token prompt (520 on GENIE-X's NPU, which adds a start token) and decodes 128 tokens; every engine except GENIE-X decodes past the model's end of turn, so every decode speed times the same 128 tokens (GENIE-X's row reaches 128 tokens on this prompt too; [METHODOLOGY.md](./METHODOLOGY.md#7-a-fixed-decode-length-where-the-engine-allows-it)). Files and quantizations are in [MODELS.md](./MODELS.md).

## Summary

| Engine | Why it exists (one line) | Shines most on | Are we measuring it there? |
|---|---|---|---|
| **llama.cpp** (llama.rn) | Portable, model-universal CPU-first inference that runs *anywhere* | **CPU**, any SoC; broadest model/quant coverage | ✅ **Yes** — CPU on all three phones, + its OpenCL GPU (Adreno) and Hexagon NPU on the POCO F8 Ultra, for all three models (not Gemma 4 E2B on the Galaxy S23; llama.rn 0.13.0-rc.8) |
| **ExecuTorch** (rn-executorch) | Ship the exact PyTorch model on-device with delegate acceleration | **XNNPACK CPU** (mobile), + Qualcomm/CoreML NPU **delegates** | ⚠️ **Partial** — XNNPACK CPU only, for Gemma 4 E2B and Qwen3 1.7B (react-native-executorch 0.10.7) |
| **LiteRT-LM** (Google AI Edge) | One runtime, vendor-accelerated across the fragmented SoC landscape | **NPU** (Qualcomm/MediaTek/Tensor), then GPU | ⚠️ **Partial** — CPU for all three models (not Qwen3 1.7B on the Galaxy S23), and the POCO F8 Ultra's NPU for Gemma 3 1B, the only board model with a Google file compiled for these phones' NPUs at the pinned revisions (LiteRT-LM 0.18.1); its GPU is measured only in an [experiment](./docs/experiments/litert-accelerators.md) |
| **GENIE-X** (Qualcomm) | Squeeze max perf/efficiency out of Snapdragon Hexagon NPUs | **Qualcomm Hexagon NPU** on flagship Snapdragons | ✅ **NPU measured** for Qwen3 1.7B on the POCO F8 Ultra (geniex-android 0.8.0, in the app); Qualcomm publishes no GENIE-X NPU file of the other two models, nor one of Qwen3 1.7B for the Galaxy S23 |
| *MLX* (Apple) | Array/ML framework native to Apple silicon | **Apple GPU (Metal)**, M-/A-series | ➖ Cited-only (no iOS/macOS benchmark app) |
| *Core ML* (Apple) | Apple's runtime targeting the Neural Engine | **ANE** | ➖ Cited-only |
| *Apple Foundation Models* | Apple's built-in system LLM | **ANE** | ➖ Cited-only |

Verdict at a glance: **llama.cpp and GENIE-X are measured at their best; LiteRT-LM is on one Qualcomm NPU for one model, and ExecuTorch on its CPU path only.** The board must keep saying so for the ⚠️ engines.

## The headline finding: on this board, only llama.cpp runs all three models on one NPU

On the POCO F8 Ultra's Hexagon v81 NPU, three engines run the board's models. For the two vendor stacks, what each can run on this board is set by the files its vendor publishes compiled for this chip, at the revisions [MODELS.md](./MODELS.md) pins:

- **llama.cpp's Hexagon backend runs the same Q4_0 GGUF files it runs on the CPU, so it runs all three board models.** With llama.rn 0.13.0-rc.8, the NPU prefills 13× (Gemma 4 E2B Q4_0 (QAT): 1688.3 against 129.8 tok/s), 12× (Qwen3 1.7B Q4_0: 2514.1 against 203.4) and 9× (Gemma 3 1B Q4_0 (QAT): 3634.7 against 404.7) faster than the CPU with the same build and file. It decodes faster than the CPU for Gemma 4 E2B (31.2 against 26.7) and Qwen3 1.7B (45.1 against 35.6), and slower for Gemma 3 1B (46.6 against 50.3).
- **LiteRT-LM runs a file compiled ahead of time for the chip; of the board's models, Google publishes one for this chip for Gemma 3 1B only.** With `litertlm-android` 0.18.1, Google's SM8850 Gemma 3 1B bundle prefills at 5010.7 and decodes at 68.8 tok/s on the NPU, against 3634.7 / 46.6 for llama.cpp's Gemma 3 1B Q4_0 (QAT) GGUF on the same NPU; LiteRT-LM's int4 `.litertlm` file runs at 661.7 / 42.2 on the CPU. At its pinned revision, Google's Gemma 4 E2B LiteRT-LM repository has no file compiled for the SM8850 or SM8550 (its current `main` adds an uncompiled NPU file, which the board does not test), and its Qwen3 1.7B repository has no NPU file. Running the NPU path takes four pieces:
  1. the `litertlm-android` AAR;
  2. Google's NPU runtime from Google Maven, `com.google.ai.edge.litert:litert-npu-runtime-qualcomm` (2.3.0), which provides `libLiteRtDispatch_Qualcomm.so`;
  3. a QAIRT SDK whose version matches the `LITERT_REF` of that LiteRT-LM release (QAIRT 2.50.0.260828 for 0.18.1);
  4. `<uses-native-library>` declarations in the app manifest (`libcdsprpc.so` for the NPU; `libOpenCL.so` and `libvndksupport.so` for the GPU).

  A mismatch fails with opaque errors: a dispatch library built for a different `LITERT_REF` logs `Unsupported dispatch runtime version`, and the Kotlin API reports only a generic `Failed to create engine`. Google's SM8550 Gemma 3 1B bundle (`Gemma3-1B-IT_q4_ekv1280_sm8550.litertlm`, built with QAIRT 2.34.0) loses prompt content after the first 128-token prefill chunk on the Galaxy S23, so probes whose fact comes after that chunk get wrong answers ([LiteRT-LM#3508](https://github.com/google-ai-edge/LiteRT-LM/issues/3508); [accelerator experiment](./docs/experiments/litert-accelerators.md)).
- **GENIE-X runs Qualcomm's own compiled bundle; of the board's models, Qualcomm publishes one for this chip for Qwen3 1.7B only.** With geniex-android 0.8.0 in the app, Qualcomm's W4A16 Qwen3 1.7B bundle prefills at 2297.1 and decodes at 27.9 tok/s, and reaches the 128-token limit in every run. llama.cpp's Qwen3 1.7B Q4_0 GGUF decodes at 35.6 tok/s on the same phone's CPU and 45.1 on the same NPU. The two are different files of the model: the bundle stores 4-bit weights and computes with 16-bit activations (W4A16), and the GGUF is Q4_0. Among phone chips, Qualcomm publishes the bundle only for the Snapdragon 8 Elite and 8 Elite Gen 5 (both labelled "for Galaxy"), and the 8 Elite Gen 5 bundle runs on the POCO F8 Ultra. Qualcomm's Gemma 4 E2B card lists only a GGUF for GENIE-X's llama.cpp plugin. The bundle needs the QAIRT 2.50 runtime it was built with; geniex-android 0.8.0 packages QAIRT 2.45 and cannot load another runtime at run time, so the app packages the 2.50 libraries in place of the AAR's ([notes](./docs/experiments/geniex-inapp.md#qairt-the-bundle-wants-250-the-aar-ships-245)).

**On the same NPU, the two vendor stacks run only the models their vendor compiled for that chip, while llama.cpp runs the same GGUF it runs on the CPU (all three board models' Q4_0 files).** A vendor bundle can be fast where it exists (for Gemma 3 1B, LiteRT-LM's bundle prefills and decodes faster than llama.cpp on the same NPU), but on this board a vendor's file list decides which models a phone's NPU runs.

## llama.cpp (via llama.rn)

- **What / who:** ggml-based C/C++ LLM inference (ggml-org / Georgi Gerganov), GGUF format. Reaches PocketPal through `llama.rn`.
- **Why it exists:** the *universal baseline* — dependency-light, portable inference that runs on essentially any CPU, with the broadest model and quant coverage and day-one support for new architectures. If a model exists as a GGUF, llama.cpp runs it.
- **Where it shines most:** **CPU**, on any SoC — hand-tuned ARM NEON / i8mm / dotprod kernels. Secondary: an **OpenCL GPU** path (Adreno) and a **Hexagon NPU** backend (`ggml-hexagon`) that runs a normal GGUF on the DSP with no vendor SDK.
- **Where it's *not* the point:** GPU/NPU are secondary and uneven — OpenCL only initializes on Adreno (not Mali/Tensor), and Hexagon exists only on Snapdragon.
- **Hexagon output by llama.rn version** (POCO F8 Ultra, `HTP0`, checked against llama.cpp on the CPU with the same model file):
  - **llama.rn 0.12.4 — wrong output.** Llama 3.2 1B (Q4_K_M and Q4_0) answers a ~20-token prompt correctly but degenerates into repeated fragments on every tested prompt over ~128 tokens; Gemma 3 1B (QAT Q4_0) fails even the short prompt. Evidence: [Llama 3.2](./evidence/7cd4368bf08f339b78e731c2eed789768de44f736f338ad38f06ee154c3ae478/), [Gemma 3](./evidence/c5116d95007ba6e68748d46e313728d978a891f72c12652f541c12679361a972/).
  - **llama.rn 0.13.0-rc.8 — correct output** for the board's three models: Gemma 4 E2B Q4_0 (QAT), Qwen3 1.7B Q4_0 and Gemma 3 1B Q4_0 (QAT) pass every answer probe of the output check, as do their OpenCL runs. Evidence: [Gemma 4 E2B](./evidence/658799957eefe03b73e298dc8cc43ef25d28cee8ae6d48747d3d87b46c527359/), [Qwen3 1.7B](./evidence/57c07c4b15a376c8002c9ec22a7052c1701a513b1fb3dde7fbcc024261e353d4/), [Gemma 3 1B](./evidence/54b1832f9dde54066fcd60ebd99d1bda43793b8b1e24bf2743d780f197522f90/).
- **Our coverage — ✅ measured at its best:** with llama.rn 0.13.0-rc.8 (llama.cpp b11804), the CPU on the POCO F8 Ultra, Galaxy S23 and Pixel 9, and the OpenCL GPU and Hexagon NPU on the POCO F8 Ultra, for Gemma 4 E2B, Qwen3 1.7B and Gemma 3 1B. The Galaxy S23 has no Gemma 4 E2B row: with the board's full loading (the 3.35 GB file read into memory), the app is ended for low memory while the model loads on that 8 GB phone ([memory probe](https://github.com/a-ghorbani/xebench/blob/5f4e14053854c216a9cc18c128b8d1d34f5dcd96/docs/experiments/model-refresh.md#galaxy-s23-gemma-4-e2b-memory-probe-2026-10-23)). The Pixel 9's Mali GPU and Tensor chip have no llama.cpp GPU or NPU backend. This is *why the board tilts toward llama.cpp*: CPU is its happy path, and we fully lit it up.

## ExecuTorch (via react-native-executorch)

- **What / who:** PyTorch's on-device runtime (Meta). Exports a PyTorch model to `.pte` and runs it through a small runtime with **backend delegates** — XNNPACK (CPU), and vendor delegates for Qualcomm QNN, MediaTek, Core ML, and Vulkan.
- **Why it exists:** the **PyTorch author-to-device pipeline** — ship the *exact* model you trained/researched in PyTorch (including custom architectures), with delegate-based hardware acceleration. It's Meta's official Llama-on-device path.
- **Where it shines most:** on mobile, **XNNPACK CPU** with 4-bit weights and 8-bit dynamic activations. For Qwen3 1.7B, react-native-executorch 0.10.7's `4-bit weights, 8-bit activations` file prefills faster than llama.cpp's Q4_0 GGUF on the CPU on all three phones (POCO F8 Ultra 323.0 against 203.4 tok/s; Galaxy S23 159.8 against 136.6; Pixel 9 159.6 against 150.8) and decodes faster on the Galaxy S23 (23.3 against 20.2) and Pixel 9 (18.3 against 17.7). Its bigger differentiator is the **delegate NPU story** (Qualcomm/Core ML) for teams who export for it.
- **Where it's *not* the point:** a model whose export leaves much of the work outside XNNPACK. Software Mansion's Gemma 4 E2B export (`mixed 4/16-bit`) keeps attention and the per-layer-embedding projections in 16-bit and runs many steps outside the XNNPACK kernels: it decodes at 6.9 tok/s on the POCO F8 Ultra, 6.7 on the Galaxy S23 and 4.9 on the Pixel 9, against 31.3, 23.3 and 18.3 for the Qwen3 1.7B export on the same runtime. The gap is in that export, not in a setting of the benchmark app ([host analysis](https://github.com/a-ghorbani/xebench/blob/c5b705ca7bad7f60b8fb68a50c2790df0e3dc69d/docs/experiments/model-refresh.md#executorch-gemma-4-e2b-why-it-decodes-slowly-host-analysis-2026-10-23)).
- **Our coverage — ⚠️ partial:** with react-native-executorch 0.10.7 (ExecuTorch 1.4.1), XNNPACK on the CPU on all three phones, for Gemma 4 E2B and Qwen3 1.7B (the Android exports Software Mansion publishes for the binding; there is no Gemma 3 1B setup, [#43](https://github.com/a-ghorbani/xebench/issues/43)). The files are XNNPACK exports, and the benchmark app packages ExecuTorch's XNNPACK backend only, so its delegate path — a real part of why it exists — is unmeasured. Honest, but incomplete.

## LiteRT-LM (Google AI Edge)

- **What / who:** Google's on-device runtime (the TensorFlow Lite successor) plus an LLM layer. Converts to `.litertlm`; runs on CPU (XNNPACK), **GPU (ML Drift)**, and **NPU** (Qualcomm QNN / MediaTek NeuroPilot / Google Tensor) through a common CompiledModel/delegate API.
- **Why it exists:** to solve the **fragmented-SoC problem** — convert once, run *vendor-accelerated everywhere*, without hand-writing kernels per chip. Its headline program is cross-vendor **NPU** acceleration.
- **Where it shines most:** **the NPU.** Google's own figures: ~1600 pp / 28 dec on a Dimensity 9500 NPU — **up to 12× CPU and 10× GPU**. On the POCO F8 Ultra, its SM8850 Gemma 3 1B bundle prefills and decodes faster than llama.cpp's Gemma 3 1B Q4_0 (QAT) GGUF on the same NPU (5010.7 / 68.8 against 3634.7 / 46.6 tok/s; see the headline above). On the CPU, Google's Gemma 4 E2B file (`mixed 2/4/8-bit`) prefills and decodes faster than llama.cpp's Q4_0 (QAT) GGUF on the POCO F8 Ultra (259.3 / 29.7 against 129.8 / 26.7 tok/s) and the Pixel 9 (176.9 / 19.3 against 93.5 / 11.9); its weights mix 2-, 4- and 8-bit, so it is a smaller file than the 4-bit GGUF. For Gemma 3 1B (LiteRT-LM's int4 `.litertlm` against llama.cpp's Q4_0 (QAT) GGUF), LiteRT-LM prefills faster on the POCO F8 Ultra (661.7 against 404.7) and decodes faster on the Galaxy S23 (38.0 against 22.6) and the Pixel 9 (26.1 against 19.3).
- **Where it's *not* the point:** **CPU**, for some files. Qwen3 1.7B's int4 `.litertlm` file (`litert-community/Qwen3-1.7B`, 4-bit weights with 32-bit activations) runs at 91.7 / 10.6 tok/s on the POCO F8 Ultra and 51.6 / 6.7 on the Pixel 9, against 203.4 / 35.6 and 150.8 / 17.7 for llama.cpp's Q4_0 GGUF. For Gemma 3 1B, llama.cpp prefills faster on the Galaxy S23 (271.7 against 221.6) and the Pixel 9 (302.1 against 205.2) and decodes faster on the POCO F8 Ultra (50.3 against 42.2).
- **Our coverage — ⚠️ one NPU, no GPU:** the board's LiteRT-LM rows are measured with LiteRT-LM 0.18.1: Gemma 4 E2B, Qwen3 1.7B and Gemma 3 1B on the CPU (POCO F8 Ultra, Galaxy S23, Pixel 9), and Gemma 3 1B on the POCO F8 Ultra's NPU (Google's SM8850 bundle). The Galaxy S23 has no Qwen3 1.7B row: its only session ran while the phone was charging, and the run conditions exclude charging because it changes the phone's clock and thermal behaviour. Every row passes the output check and decodes 128 tokens. The NPU row's backend is confirmed from the app's own log: a QNN HTP context created from the bundle for each load; the dispatch library and HTP backend loaded earlier in the same process ([rule](./docs/RUN-CONDITIONS.md#litert-lm-npu-backend-confirmed-by-the-apps-log-litert-npu-log-v1)). The Galaxy S23 has no NPU row: its SM8550 bundle gives wrong output ([LiteRT-LM#3508](https://github.com/google-ai-edge/LiteRT-LM/issues/3508)). The GPU path is measured only in the [accelerator experiment](./docs/experiments/litert-accelerators.md): nothing in the record confirms that the GPU executes. It needs the `<uses-native-library>` declarations for `libOpenCL.so` / `libvndksupport.so` that the LiteRT-LM Kotlin guide requires ([LiteRT-LM#1860](https://github.com/google-ai-edge/LiteRT-LM/issues/1860)). MediaTek and Tensor NPUs are not on the board.

## GENIE-X (Qualcomm)

- **What / who:** Qualcomm's on-device GenAI SDK (GENIE-X, `com.qualcomm.qti:geniex-android`). Runs LLMs on Snapdragon through its own QAIRT pipeline on the QNN C API on the **Hexagon NPU**, with a `llama.cpp` CPU plugin as a compatibility fallback.
- **Why it exists:** to extract **maximum performance and power-efficiency from Qualcomm Snapdragon NPUs** — first-party Hexagon acceleration tuned to the SoC's HTP units and power envelope.
- **Where it shines most:** the **Qualcomm Hexagon NPU** on flagship Snapdragons, with the bundles Qualcomm AI Hub compiles per chip. That is the whole product.
- **Where it's *not* the point:** its CPU (`llama_cpp`) plugin is a fallback/compat path — it is llama.cpp, so the board measures llama.cpp directly instead and uses the plugin only as the reference of GENIE-X's output check; non-Qualcomm silicon is out of scope entirely.
- **Our coverage — ✅ NPU measured:** geniex-android 0.8.0 in the benchmark app, with Qualcomm's W4A16 Qwen3 1.7B bundle (QAIRT 2.50.0.260828221209) on the POCO F8 Ultra's Hexagon v81: 2297.1 / 27.9 tok/s, 128 tokens decoded in every run (GENIE-X has no option to decode past the end of turn; this prompt does not reach it). Its prefill speed is derived from the time to the first token, because the QAIRT plugin reports no separate prefill time. The backend is confirmed from the app's own log ([rule](./docs/RUN-CONDITIONS.md#genie-x-npu-backend-confirmed-by-the-apps-log-geniex-npu-log-v1)). Among phone chips, Qualcomm publishes the Qwen3 1.7B bundle only for the Snapdragon 8 Elite and 8 Elite Gen 5 (for Galaxy), not for the Galaxy S23's SM8550, and publishes no GENIE-X NPU bundle of Gemma 4 E2B or Gemma 3 1B, so this is the board's only GENIE-X row ([notes](./docs/experiments/geniex-inapp.md)).

## Apple-silicon engines (MLX, Core ML, Apple Foundation Models)

- **MLX** — Apple's array/ML framework; shines on the **Apple GPU (Metal)** on M-series/A-series. **Core ML** — Apple's runtime; shines on the **ANE (Apple Neural Engine)**. **Apple Foundation Models** — Apple's built-in system LLM (ANE).
- **Our coverage — ➖ cited-only:** iOS/macOS-only, and we have no iOS benchmark app, so these appear on the board *only* as vendor/community-cited numbers, never as our measurements. Honest, but it means the entire Apple-accelerator story is unverified by us.

## Reading the comparison honestly

1. **The board covers each engine's paths unevenly.** llama.cpp is measured on CPU, GPU (OpenCL) and NPU (Hexagon); GENIE-X on the NPU (one row); LiteRT-LM on CPU and on one Qualcomm NPU, for Gemma 3 1B on the POCO F8 Ultra; ExecuTorch on CPU only. LiteRT-LM's GPU is measured only in the [accelerator experiment](./docs/experiments/litert-accelerators.md), and no MediaTek or Tensor NPU is measured; the Apple engines are cited-only. Where an engine's accelerated path is missing, its CPU rows understate it.
2. **Therefore the board must say so.** Where a card shows an engine only on CPU, it should carry an explicit note: *"shown CPU-only; its NPU/accelerated path — the reason it exists — is unmeasured here."* Implying a fair fight we haven't run is the thing to avoid.
3. **A cross-engine winner claim is only valid within the same backend class and phone, and names the files.** The engines run different files of the same model: "LiteRT-LM beats llama.cpp on Gemma 4 E2B" holds *on CPU* on the POCO F8 Ultra and the Pixel 9, for LiteRT-LM's `mixed 2/4/8-bit` `.litertlm` against llama.cpp's Q4_0 (QAT) GGUF; it says nothing about another file, phone or backend. The quantizations differ in more than bit width: ExecuTorch's files compute with 8-bit activations, GENIE-X's W4A16 bundle with 16-bit activations, and the two Gemma 4 E2B files outside llama.cpp mix bit widths ([MODELS.md](./MODELS.md#gemma-4-e2b-and-qwen3-17b-board-models)).

## Coverage gaps (what each engine needs for a fair shot)

| Priority | Gap | Status / concrete unblock |
|---|---|---|
| **1** | LiteRT **NPU** for the other models, and **GPU** rows | The NPU row needs a file compiled for the chip: Google publishes Gemma 3 1B bundles for the SM8850 and SM8550, and no Gemma 4 E2B or Qwen3 1.7B file for either. Stack: `litertlm-android` 0.18.1 + `com.google.ai.edge.litert:litert-npu-runtime-qualcomm:2.3.0` (Google Maven) + QAIRT 2.50.0.260828 (public Community download) + `<uses-native-library>` manifest declarations (`libcdsprpc.so` for NPU; `libOpenCL.so` and `libvndksupport.so`, `required="false"`, for GPU). The Galaxy S23 NPU row needs a fixed SM8550 bundle ([LiteRT-LM#3508](https://github.com/google-ai-edge/LiteRT-LM/issues/3508)). A GPU row needs evidence that the GPU executes. |
| **2** | LiteRT NPU on **MediaTek** | **Untested.** Google publishes the runtime (`litert-npu-runtime-mediatek:2.3.0`), but LLM bundles exist only for MT6989 / MT6991 / MT6993. Our **klee** (POCO X8 Pro) is **MT6899**, so it has no bundle. (GENIE-X is Qualcomm-only, N/A on MediaTek.) |
| **3** | ExecuTorch **delegate** (NPU) | Needs a QNN export of a board model and the QNN backend packaged in the app; the app packages XNNPACK only. |
| **4** | GENIE-X on more models and chips | Needs Qualcomm AI Hub bundles: among phone chips, Qwen3 1.7B exists only for the Snapdragon 8 Elite and 8 Elite Gen 5 (for Galaxy); Gemma 4 E2B has a GGUF only. |
| **5** | Apple engines (MLX / Core ML / Foundation Models) | Build an iOS/macOS benchmark app so these are *measured*, not just cited. |

On one NPU, llama.cpp runs every model the board measures, and the two vendor stacks run the models their vendor compiled for the chip (at the pinned revisions), fast where a file exists. LiteRT-LM also needs four version-matched pieces and has one published bundle with wrong output; GENIE-X needs the QAIRT runtime its bundle was built with. That contrast in model coverage and integration friction is the board's headline finding.
